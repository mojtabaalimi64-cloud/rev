# معماری جداسازی REV Website و REV App

## تصمیم معماری

وب‌سایت REV و اپلیکیشن REV باید از نظر رابط کاربری، کد قابل انتشار، چرخه انتشار، نسخه‌بندی و امکان توقف، مستقل باشند. این تصمیم عمداً امکان لغو اپلیکیشن را بدون بازگرداندن یا مختل‌کردن سایت فراهم می‌کند.

### آنچه مستقل است
- مخزن/پوشه یا پروژه انتشار جدا برای اپلیکیشن
- تنظیمات ساخت، محیط آزمایش و انتشار جداگانه
- دامنه یا مسیر میزبانی مجزا برای نسخه آزمایشی اپ
- شماره نسخه و فرایند rollback مستقل
- رابط کاربری و ناوبری مختص موبایل
- قابلیت feature flag برای غیرفعال‌کردن امکانات آزمایشی اپ
- گزارش خطا و شاخص‌های استفاده از اپ به‌صورت جداگانه، با رعایت حریم خصوصی

### آنچه می‌تواند مشترک بماند
- APIهای پایدار و کنترل‌شده REV
- پایگاه داده و هویت حساب کاربری، در حدی که قرارداد API و مجوزها اجازه دهند
- داده‌های خودرو، ایستگاه، کسب‌وکار و محتوای عمومی
- منطق تجاری مشترک در سمت سرور

اشتراک backend به معنی وابستگی انتشار نیست. اپ باید بتواند مستقل منتشر یا متوقف شود؛ اگر اپ قابلیت خاصی لازم دارد، ابتدا باید قرارداد API و مجوز آن بررسی شود. تغییرات ناسازگار API نباید بدون نسخه‌بندی یا سازگاری عقب‌رو منتشر شوند.

## ساختار پیشنهادی

```text
REV
├── Website (موجود، انتشار مستقل)
│   ├── دسکتاپ و وب واکنش‌گرا
│   ├── پنل مدیریت و گزارش‌های کامل
│   └── محتوای REV، خودروها، خدمات و برنامه‌ریز سفر
├── App (پروژه/انتشار جدا، ابتدا آزمایشی)
│   ├── تجربه موبایل و ناوبری مختص موبایل
│   ├── نقشه، GPS و کارهای سریع سفر
│   └── امداد جاده‌ای و اعلان‌ها پس از آماده‌شدن backend
└── API و داده مشترک
    ├── احراز هویت و مجوز سمت سرور
    ├── خودروها، ایستگاه‌ها، کسب‌وکارها و محتوا
    └── درخواست‌ها و گزارش‌ها با دسترسی نقش‌محور
```

## راهبرد انتشار و لغو

1. **هیچ تغییر آزمایشی اپ مستقیماً روی شاخه انتشار سایت اعمال نشود.**
2. توسعه اپ در شاخه و ترجیحاً پروژه/دایرکتوری جدا انجام شود. برای انتشار نهایی اپ از workflow جدا استفاده شود.
3. ابتدا یک نسخه داخلی/آزمایشی برای بررسی روی دستگاه‌های واقعی آماده شود. صرف وجود شاخه Git به معنی داشتن URL پیش‌نمایش نیست؛ محیط preview باید جداگانه تنظیم شود.
4. اپ از APIهای موجود با درخواست‌های احراز هویت‌شده استفاده کند؛ هیچ secret یا کلید خصوصی داخل کد عمومی قرار نگیرد.
5. قابلیت‌های پرریسک یا هنوز آزمایشی با feature flag سمت سرور کنترل شوند.
6. قبل از انتشار، آزمون‌های regression سایت و API اجرا شوند.
7. در صورت عدم موفقیت، انتشار اپ متوقف شود، اپ/صفحه معرفی آن از دسترس جدید خارج شود و feature flagهای مربوط غیرفعال شوند. وب‌سایت اصلی و داده‌های آن دست‌نخورده باقی بمانند.
8. حذف اپ نباید موجب حذف حساب کاربر، سفرها، محتوای سایت یا داده‌های مشترک شود. پاک‌سازی داده‌های اختصاصی اپ فقط با سیاست نگهداری و تأیید جداگانه انجام شود.

## نکته درباره PWA و APK

PWA یک اپ وب نصب‌پذیر است و معمولاً با انتشار نسخه وب به‌روزرسانی می‌شود؛ اما اگر هدف جداسازی کامل انتشار اپ از سایت باشد، PWA روی همان سایت و همان deployment به‌تنهایی این جداسازی را تضمین نمی‌کند. PWA می‌تواند در origin/مسیر مستقل و با workflow مستقل میزبانی شود، یا بعداً یک اپ اندروید بسته‌بندی‌شده با چرخه انتشار جدا ساخته شود.

تصمیم نهایی بین PWA مستقل و اپ Android (مثلاً wrapper مبتنی بر WebView/Capacitor) باید بعد از نمونه اولیه و ارزیابی نیازهای GPS، اعلان‌ها، اجرای پس‌زمینه، انتشار و نگهداری گرفته شود. در مرحله اول نباید بازنویسی کامل سایت یا تعهد به انتشار APK را فرض کنیم.

## معیارهای پذیرش
- انتشار یا rollback اپ هیچ commit یا deployment جدیدی در سایت ایجاد نکند.
- اپ را بتوان خاموش یا از انتشار خارج کرد، در حالی که سایت و پنل مدیریت کار کنند.
- شکست اپ باعث مهاجرت مخرب یا تغییر ناسازگار در دیتابیس مشترک نشود.
- همه APIها مجوز سمت سرور داشته باشند؛ پنهان‌کردن دکمه در رابط به‌تنهایی کنترل دسترسی نیست.
- کلیدهای محرمانه در مخزن عمومی قرار نگیرند.
- اپ و سایت تست‌های smoke/regression جداگانه داشته باشند.
- نسخه آزمایشی تا زمان تأیید مالک محصول به کاربران عمومی معرفی نشود.
